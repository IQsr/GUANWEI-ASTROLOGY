# 轉場同首次載入審查（2026-11-14）

起因：Issac 話「有啲 transition 位會 lag lag 地，特別係第一次入嘅時候」。
呢份文件記低量到嘅數字、原因同建議。**只改咗一樣細嘢（第 6 項），其餘全部等你揀。**

## 一、結論：最值得做嘅三樣

| 次序 | 問題 | 量到 | 屬於邊類 |
|---|---|---|---|
| 1 | **中文字體太重，喺入場動畫行緊嗰陣先到** | 中文首頁第一次入要載 24–25 片字體、共 **1.8MB**；手機 4G 要到 **3.2 秒**先齊，標題個墨滲動畫（1.6 秒）用住後備字體行完，之後先換字 | 字體遲到 |
| 2 | **server 間中要 2.5–5.6 秒先回**（起盤、第一次入章節） | 落印個 action：一次 5.6 秒、其餘 1.4–1.6 秒；入章節：三次 2.4–3 秒以上、其餘 0.13–0.2 秒 | 網絡／TTFB |
| 3 | **轉頁嗰下成版凍住，冇任何反應** | 書齋／藏經閣／設定／目次之間每次轉頁，畫面凍 250–470ms（手機最長 617ms）先開始淡入；章節、目次超過 400ms 就會「淡入舊版 → 新版彈出嚟」 | 動畫設計＋每次都要問 server |

第 1 樣只影響「第一次入」，同你講嘅感覺最吻合。第 2 樣係間歇性，但測試者人少、站冷，撞到嘅機會高。第 3 樣係每一次轉頁都有。

## 二、點樣量

- 內置瀏覽器 pane 喺背景，量唔到畫面數字（冇 paint、冇 LCP），所以改用本機 **headless Chromium（Playwright）** 對住正式站 `guanwei-astrology.vercel.app` 量。
- 兩個設定：
  - **桌面**：1366×800，唔限速。
  - **手機**：375×812、CPU 慢 4 倍、Fast 4G（下行 9Mbps、延遲 150ms）—— 模擬中階 Android。
- 每版裝 `PerformanceObserver`（LCP、layout-shift、longtask）、逐格 `requestAnimationFrame` 時間、resource timing、`document.getAnimations()`；首頁另外錄咗一次 trace 睇主線程做緊乜。
- 轉頁時間由「撳」嗰刻計到網址變（新頁 commit）。
- 路線：首頁（`/`、`/en`）冷快取 → 起盤 → 落印 → 題名幕 → 揭開 → 目次 → 章節 → 下一章 → 書齋／藏經閣／設定。
- 量度機喺英國入口（`lhr1`），server 喺都柏林（`dub1`）。

### 量唔到／要留意

- **真 iPhone Safari 冇量。** Safari 冇 `interpolate-size`（卷軸唔展開）、`backdrop-filter` 同 view transition 嘅表現都唔同 Chrome，要真機睇。
- **香港／亞洲讀者嘅延遲冇量。** 我呢邊去 server 好近；香港去都柏林每次來回多二三百毫秒，下面所有「問 server」嘅數字喺香港會更差。
- **逐格掉格數字唔可靠。** headless 用軟件畫圖，桌面成日見到 33ms 一格，唔代表真機。所以下面講「掉格」只用 long task 同超過 100ms 嘅凍結，唔用 33ms 嗰啲。
- `backdrop-filter` 嘅合成成本量唔到（同上）。
- 2.5 秒以上嗰幾次慢回應：後來用實驗核實咗係 serverless 冷啟動（見第 2 項嘅補充）。

## 三、問題清單（按影響排）

### 1. 中文字體：1.8MB，喺入場動畫中途先到 ★

- **喺邊度**：第一次入中文首頁；第一次入目次、藏經閣亦有第二、三波。
- **數字**：

  | 版 | 字體片數 | 大細 | 手機幾時齊 |
  |---|---|---|---|
  | `/`（中文）第一次 | 24–25 | 1.82–1.88MB | 3.2 秒 |
  | `/en` 第一次 | 6–10 | 0.4–0.7MB | 1.9 秒 |
  | 第一次入目次 | 再多 11–19 | 0.48–0.93MB | 撳後 2.5 秒 |
  | 第一次入藏經閣 | 再多 16–17 | 1.2–1.3MB | 撳後 1.8 秒 |

  手機首頁：FCP 1.37 秒，字體 0.85–3.2 秒陸續到，全部喺 3.4 秒先換字。標題 `moshen` 由 1.4 秒行到 3.0 秒，即係**成個墨滲動畫都係後備字體**，動畫完咗先變返宋體。字體到嗰陣仲有 7 次重新排版（每次 34–103ms，trace 2.5–3.3 秒），啱啱撞正 `mu-in` 嗰幾行字入場。
  CLS 係 0（中文字闊度一樣，冇跳位），所以問題係「閃」同「窒」，唔係「跳」。
- **原因**：`apps/web/src/app/fonts.ts:25` 用 Fontsource **可變字型**，每片 50–110KB（靜態單一字重嘅片細好多）；首頁同時用宋體（13 片）同黑體（11 片）。檔頭寫「讀者一版通常只下載幾十 KB」，實際係 1.8MB。`font-display: swap`。
- **建議**（揀一樣或者夾埋）：
  - a. 中文**黑體改用系統字**（PingFang／微軟正黑／Noto Sans CJK），只留宋體做標題同正文 —— 即刻少 11 片、約 750KB。視覺變化最細。
  - b. 宋體由可變字型改做**靜態兩個字重**（400、600），每片細一半左右。
  - c. 首頁標題嗰幾個固定字，build 時切一個幾 KB 嘅細字體檔再 preload，墨滲一開始就係啱嘅字。
- **影響**：大。係「第一次入」最明顯嘅一樣。

### 2. server 間中要 2.5–5.6 秒先回 ★

- **喺邊度**：落印（起盤）；目次 → 第一章。
- **數字**：
  - 落印 `castChart`：5633ms（當日第一次）、1413ms、1583ms。
  - 入章節 TTFB：>3000ms、2420ms、2501ms 各一次；其餘十幾次 122–209ms。
  - 直接攞成版（暖）：書齋 266–584ms（第一次 1240ms）、目次 427–624ms、命宮章 334–457ms、福德章 561–741ms。
- **原因**：全部係 `force-dynamic`（`shelf/page.tsx:54`、`book/[bookId]/page.tsx:64`、`[chapter]/page.tsx:61`），每次都要行 function。慢嗰幾次似冷啟動（`cast/actions.ts` 同章節頁都拉住成個規則庫同詞條庫）。起盤暖嘅時候都要 1.4 秒：排盤＋寫 19 章＋入 DB 喺同一個 action（`cast/actions.ts:95-170`）。
- **落印嗰下讀者見到乜**：卷軸收埋要 2.4 秒（1300ms 等＋1100ms 捲），所以 1.4 秒嘅 action 俾動畫遮住，冇問題；但 5.6 秒嗰次，卷軸收完之後有 3 秒幾乎冇嘢郁。
- **建議**：
  - a. 先去 Vercel log 確認係咪冷啟動（我冇核實）。係嘅話：開 Fluid Compute／保溫，或者用排程每幾分鐘打一次 `/shelf` 同一個章節。
  - b. 落印之後如果超過約 3 秒未回，出一句「正在排盤⋯」之類嘅字，唔好齋等。
  - c. 目次頁預先暖章節 function（例如目次一載入就背景 fetch 第一章）。
- **影響**：大，但係間歇性。測試者少、站冷嗰陣特別容易撞到。

#### 2 嘅核實（2026-11-14 補）：係冷啟動，一次約 5 秒

Vercel 係 Hobby 計劃，runtime log 只留一個鐘、而且只有 console 輸出，睇唔到每個請求嘅啟動類型；所以改用實驗核實：

- **靜咗 43 分鐘之後第一個請求**：書齋 **5680ms**；緊接住目次 911ms、章節 670ms，第二輪起全部返回 300–510ms。即係冷啟動約 5.3 秒，而且書齋、目次、章節共用同一個暖咗嘅 instance。
- **同一時間 8 個章節請求**（站已經暖）：第一輪 920、1209、1233、**4745、5480、5481、5596、5597**ms；第二輪全部 960–1161ms；第三輪又有一個 3989ms。即係 **一個 instance 一次只接一個請求，同時嚟多幾個，Vercel 就開新 instance，每個新開嘅都要冷啟動**。
- 呢個解釋到點解「活躍緊都撞到」：**目次一出，Next 會同時 prefetch 畫面上十幾條章節連結**（量到 5–11 個 `_rsc` 請求同一刻發出，每個只攞到 0.5KB 空殼，冇用），逼 Vercel 開一批新 instance；讀者跟住撳第一章，就有機會派去一個仲啟動緊嘅 instance —— 所以先至有 2.4–3 秒以上嗰幾次。
- **點解冷啟動要 5 秒**：章節頁個 function 追蹤到 654 個檔、共 **33MB**，入面一個 **13.6MB 嘅 JS chunk**（成個規則庫同詞條庫），另外幾個 1–3MB 嘅 JSON（`cards/ming.json` 3.3MB、`palace-remaining.json` 1.9MB、`synthesis/cards.json` 1.7MB、`synth-tr.json` 1.0MB）。每次冷啟動都要讀晒、parse 晒。
- **Fluid Compute**：Issac 確認本身已經開咗（2026-11-14）。即係開咗都照樣會喺一批請求同時到嗰陣開新 instance（上面嗰個實驗就係喺開咗嘅情況下量嘅），所以唔可以靠佢解決。

**建議（由易到難）**：

1. ~~開 Fluid Compute~~ —— 已經開咗，冇得再做。
2. **本書入面嘅連結關咗 prefetch**（目次嗰十幾條、`PageTurnLink`）：呢啲頁係 `force-dynamic` 又冇 `loading.tsx`，prefetch 只攞到空殼，淨係得個「逼開新 instance」嘅壞處。改動細（`<Link prefetch={false}>`）。 **已做（2026-11-14）**：`PageTurnLink`（只限 `/book/…`，示範書照舊）、`Juanshou` 返目次、`ShiyanCard`、`DingshiCard`。

   **merge 之後重量（2026-11-14，正式站 `0390e82`，桌面，每輪新 context 入目次再撳命宮）**：

   | | 目次後 `/book/` prefetch | 撳命宮後 TTFB | 換到頁 | 慢（>2 秒）嘅次數 |
   |---|---|---|---|---|
   | 改之前 | 2 個（捲落去會再多） | 186–283ms；慢嗰兩次 2351、2951ms | 706–1072ms；慢嗰兩次 3036、3726ms | 6 次有 2 次 |
   | 改之後 | 0 個 | 116–172ms | 524–950ms | 8 次有 0 次 |

   樣本細（6 輪對 8 輪），但方向清楚。目次仲有 4 個 prefetch 係導覽條嗰啲（書齋、設定都係即場計），冇郁。
   靜咗一排之後第一個請求照舊要 4–5.7 秒（今次暖機量到 3935ms），呢樣關 prefetch 幫唔到。
3. **保溫**：用排程每幾分鐘打一次 `/shelf`。Hobby 嘅 Vercel Cron 最密一日一次，要用外面嘅排程（例如 GitHub Actions 每 5 分鐘）。治標，但對「測試者第一下入嚟」最直接。
4. **縮細 function**：英文、日文譯表同綜合判讀卡改做用到先讀（而家一啟動就全部載入）。治本，但係中等改動，要量過先知慳幾多。

### 3. 轉頁嗰下成版凍住 ★

- **喺邊度**：所有經 `PageFade` 嘅轉頁（導覽條、書齋、藏經閣、設定、書脊 → 目次、章節 → 目次）。
- **數字**（撳 → 新頁出現；括號係最長凍結一格）：

  | 轉頁 | 桌面 | 手機 |
  |---|---|---|
  | 藏經閣 → 書齋 | 294–329ms（283–317） | 323–465ms（317–467） |
  | 書齋 → 設定 | 246–312ms（233–300） | 255–520ms（250–433） |
  | 設定 → 書齋 | 262–279ms（250–267） | 288–321ms（283–317） |
  | 書齋 → 本書（書脊） | 629ms（400） | 703ms（617） |
  | 章節 → 目次 | 512ms（400） | 440ms（400） |
  | 書齋 → 藏經閣（靜態頁） | 63–91ms | 222–413ms |
  | 首頁 → 起盤（靜態頁） | 93ms | 228ms |

  對照：關咗 view transition 再量，轉頁時間一樣（245–396ms），但最長一格得 17–50ms —— 即係**慢嘅係等 server，凍嘅係 view transition**。
- **原因**：
  - `PageFade.tsx:31,65-70`：`startViewTransition` 影低舊頁之後成版停畫，等新頁到（最多 `WAIT_MS` 400ms）先淡入 180ms。等嗰段撳落去冇任何反應。
  - 超過 400ms（目次、書脊）：到時限就照淡入，但新頁未到，變成「凍 400ms → 舊版淡入舊版 → 新版突然換」。
  - 動態頁冇 `loading.tsx`，prefetch 只攞到 0.4KB 空殼；router 快取亦冇設 `staleTimes`，所以**返去啱啱睇過嘅書齋都要再問 server 一次**。
- **建議**：
  - a. `next.config` 加 `experimental.staleTimes.dynamic`（例如 30 秒）：來回書齋／設定／目次即刻有，唔使再等。改動細，但書齋資料會有最多 30 秒舊（改名、刪書之後要 `router.refresh()`）。
  - b. 撳嗰刻俾即時反應（連結變色／導覽條一條幼進度線），唔好齋凍。
  - c. `WAIT_MS` 400 → 約 250，或者動態頁加 `loading.tsx` 骨架，等淡入有嘢可以淡去。
- **影響**：中至大。每次轉頁都有，香港讀者會再慢二三百毫秒。

### 4. 第一次打開目次：手機卡 0.8–1 秒

- **喺邊度**：題名幕「讀下去」→ 目次；書脊 → 目次。
- **數字**：手機有一個 835ms 嘅 long task、一格凍 967ms（書脊入：581ms／617ms）；桌面 92–127ms。同時載 11–19 片字體。
- **原因**：目次頁一次過 render 命盤＋六條問題卡＋ 19 行目次，再加 19 片新字體到嗰陣重排。HTML 119KB。未細分邊樣最重。
- **建議**：做完第 1 項（字體）再量一次，睇剩幾多；仲慢先拆命盤 hydration。
- **影響**：中（只限手機、只限第一次）。

### 5. 起盤卷軸展開／收埋用 `height` 做動畫

- **喺邊度**：入 `/cast` 卷軸展開（1.4 秒）；落印後卷軸收埋（1.1 秒）。
- **數字**：動畫期間每格都有 layout-shift（展開 11–13 次、收埋約 40–50 次）；手機入 `/cast` 有 249ms＋172ms 兩個 long task、一格凍 433ms。
- **原因**：`globals.css:4447-4459` `zhou-kai`／`zhou-shou` 用 `interpolate-size` 直接郁 `height`，每格都要重新排版成幅卷軸（有紙紋底、成個表單）。
- **建議**：改用 `clip-path: inset()` 或者 `transform: scaleY` 遮住展開，唔郁 height；或者縮短到 700–900ms。
- **影響**：中。要改動畫做法，要你睇過效果。

### 7. 首頁入場序列偏長

- **數字**：由第一格畫面起計，起盤掣 2.0 秒先完全出現，三步說明 2.3 秒。手機 FCP 1.37 秒，即係入站 **3.4 秒**先見到完整嘅掣。

- **建議**：掣提前到 600ms 左右；`mu-in` 由 900ms 縮到 600ms。純設計決定。
- **影響**：細至中。唔係 lag，但會覺得「慢」。

### 8. CSS 檔 701KB、8 個都阻住第一格

- **數字**：8 個 CSS 共 216KB（解壓 701KB），全部 render-blocking；桌面 236ms 載完，手機 743ms。頁面有 **667 個 `@font-face`**。手機第一次排版一個 long task 640ms（Layout 534ms）。
- **原因**：七套 Fontsource 字體（TC／SC／JP 各兩套＋ Playfair）嘅 `@font-face` 全部入晒每一版，繁體讀者都要載簡體同日文嗰幾百條宣告。第一次排版咁慢係咪因為呢 667 條，**未核實**。
- **建議**：按語言分開載字體 CSS（繁體頁唔載 SC／JP）。要改 `fonts.ts` 同 layout，中等改動。
- **影響**：中（手機第一格可能快幾百毫秒），要試過先知。

### 9. 章節頁每次攞晒前面所有章

- **數字**：暖嘅時候轉章 344–647ms（TTFB 122–209ms，之後串流到 333–634ms）；越後嘅章越重 —— 福德章成版 227KB、561–741ms，命宮章 94KB、334–457ms。
- **原因**：`[chapter]/page.tsx:113-149`，為咗成本書一齊標註，每次攞晒第一章到呢章嘅正文再行 `markBook`。
- **建議**：標註結果按書快取，或者成書嗰陣計好存低。屬於改資料載入方式，唔急。
- **翻頁動畫本身冇問題**：`PageTurnLink` 一撳就轉頁，翻頁期間桌面冇掉格，手機只有新頁到嗰陣一個 63–218ms 嘅 long task。
- **影響**：細（暖嘅時候）。真正慢嗰幾次係第 2 項。
